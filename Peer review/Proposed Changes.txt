Proposed change (ready-to-paste insertion at end of Section II)
--------------------------------------------------------------
To make the comparison to prior work explicit, we benchmark a set of canonical models that appear repeatedly in the remote sensing yield literature (SVR/SVM, Random Forest, LSTM/CNN-style deep models, and gradient boosting such as XGBoost/LightGBM) on a single unified Minnesota county-year dataset constructed from GLDAS+PRISM plus economic and infrastructure indicators. This yields an apples-to-apples algorithmic comparison under a fixed feature set and evaluation protocol, rather than comparing one-off models across studies. In our experiments, the best-performing model (LightGBM) achieves R^2 = 0.973 with RMSE = 2,214,708 bushels while excluding acres planted, demonstrating that fused environmental and economic proxies can compensate when the dominant acreage feature is unavailable. Table 1 below summarizes how our fused county-level covariates differ from data used in representative prior studies. For context, related studies that rely primarily on remote sensing or management/weather variables report lower predictive agreement on their respective targets and scales (e.g., Ji et al. 2022 reports mean predicted R^2 = 0.63 and best mean predicted R^2 = 0.67 for Corn Belt yield using EVI/LAI/LST; Shahhosseini et al. 2021 reports about 77% explained spatio-temporal variance for county-level yield using an ensemble CNN–DNN; and Kayad et al. 2019 reports within-field Sentinel-2 monitoring R^2 up to ~0.6 using Random Forest). Because these works differ in target (yield vs total production), spatial unit (field vs county), and available covariates, we treat cross-paper metrics as contextual rather than a direct superiority claim; our primary comparison is the unified Minnesota benchmark across the above model families.

Proposed change (ready-to-paste text to add under Section V-B, before/after Table 4)
-----------------------------------------------------------------------------------
Definition of “Importance” (LightGBM split-count importance):
In this paper, the “Importance” value reported for a feature is the LightGBM split-count feature importance computed from the final trained LightGBM ensemble. Concretely, for feature j:

Importance(j) = sum_{t=1..T} sum_{s in SplitNodes(t)} 1[ feature(s) = j ]

where T is the number of trees in the trained LightGBM model, SplitNodes(t) is the set of internal split nodes in tree t, and 1[·] is the indicator function (1 if the split uses feature j, else 0). Therefore, Importance(j) is an integer that counts how many times feature j is selected as a split variable across all trees in the ensemble (LightGBM’s default `importance_type = "split"` in the sklearn API).

How to interpret the numbers in Table 4:
- Larger values mean the model relied on that feature more frequently when constructing decision rules (more split usage across the ensemble).
- The values are unitless and primarily meaningful for ranking features within the same trained LightGBM model/dataset; they are not directly comparable across different model types or differently-configured LightGBM trainings.
- (Optional, if you want a normalized interpretation): RelativeImportance(j) = Importance(j) / sum_k Importance(k), which yields a percentage-like share of total split usage.


Rationale (one-liner)
--------------------
This explicitly defines what “Importance” is, how the table values are computed from the trained LightGBM model, and how readers should interpret the raw integers reported in Table 4.
